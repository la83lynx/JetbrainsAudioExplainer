=== case: cursor-en-skill ===
You are running headless inside the "Audio Explainer" IDE plugin. The user right-clicked "Explain This (Audio)" in their editor to get an automatic, narrated walkthrough of the code at their cursor.

This is a NON-INTERACTIVE run: there is no human to answer questions. Do NOT ask anything, do NOT wait — act autonomously and finish in one pass.

Cursor context (JSON):
{"file":"src/Services/BuildService.cs","absolutePath":"C:/work/proj/src/Services/BuildService.cs","caretLine":142,"selectionText":null,"projectRoot":"C:/work/proj"}

Follow the headless flow documented here (read it first):
  /home/u/.claude/skills/audio-explainer/docs/explain-at-cursor.md
The `set_plan` schema is documented ONCE, authoritatively — read it before writing the plan:
  /home/u/.claude/skills/audio-explainer/docs/plan-schema.md
The helpers that POST the plan are in /home/u/.claude/skills/audio-explainer/scripts/ (explainer.ps1 on Windows, explainer.sh elsewhere).

What to do:
1. Read in/around the cursor and expand to the enclosing method/class — YOU do the symbol resolution.
2. Build a lean `set_plan` (usually 1-2 frames) with dense, pointer-style steps and good plain-text `ttsText`, following docs/plan-schema.md exactly. A plan is `frames` (each one a file plus the `keep` ranges visible in it — header rows as "context", the member itself as "focus") plus `steps` (the narration, in order, each naming its frame and the `ranges` it lights). EVERY line a step lights must be inside its frame's `keep`. Where a one-line aside next to the code would genuinely help (a constraint, a gotcha, the reason behind a magic number), add an optional one-sentence `note` to that step — sparingly, not on every one. Where a step is really about ONE identifier, add an optional `beats` entry — {"line":N,"token":"…"} with the name copied verbatim from THAT line, so the plugin can pulse it — again sparingly. Where a concrete case would clarify a tricky transformation or a surprising result, add an optional ONE-LINE `example` ("Parse(\"2024-01\") → DateOnly(2024, 1, 1)") — one line only, and only where it teaches something the code doesn't show. Where two places are genuinely linked — a value produced on one line and consumed on another, a call whose target is in another file — add an optional frame-level `relations` entry and the plugin will draw the connection; 2-3 per frame at most, and anchor an endpoint inside the step it belongs to. Declare a link ONCE: a cross-file one is drawn as a matched pair of portals, one in each place, so give its far end both `file` and `line`. Every plan renders as a tree of code — do not send `view` at all. When the explanation IS a caller-callee chain, give each nested frame `parent`, `callLine` and `callToken` (the call line must be a line the parent keeps). When it walks over several unrelated places in turn, group the frames into `scene`s: frames sharing a `scene` are on screen together and a step in another scene replaces them, so a long walkthrough keeps a handful of files visible rather than all of them. A `parent` must be in the same `scene`.
   Use field names frames/steps/keep/ranges/start/end/ttsText — never segments/highlights/startLine/endLine/label/subHighlights.
   The top-level "language" is the walkthrough's language code ("en" if English).
3. POST it to the loopback walkthrough server (port+token in ~/.claude-explainer-port and ~/.claude-explainer-token). Use a skill helper script, or curl directly. A {"ok":true} reply = success. The reply also carries an `issues` array whenever the plan was partly dropped or degraded — READ IT: an [error] there means the user cannot see part of what you wrote (an unresolvable path, a step naming a frame that does not exist), so fix it and re-POST.
   The reply checks every token and line number against the source files, so do NOT write or run a script to validate the plan yourself — POST it and read the reply.
   Write the JSON file you POST in /tmp/audio-explainer/plans/run-0/ — never inside the project, where it would show up in the user's saved walkthroughs.
4. Do NOT print the walkthrough as terminal text and do NOT send goto/resume — just `set_plan`. Print only a one-line status when done.
=== end ===
